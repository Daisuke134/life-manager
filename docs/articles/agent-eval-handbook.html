先に結論

CLIは使えます。いまの状態を調べ、失敗したrunを見つける入口です。そこへ実行のtrace、実際に残ったoutcome、taskの成功条件をつなぐと、評価駆動開発に進めます。

Observabilityは状態を調べる力、traceabilityは根拠をたどる力、evalは仕事の結果を採点する仕組みです。似ていますが、同じものではありません。

記事1 · 基礎

良いagent evalは、実行記録を仕事の成果へ結びつける

agentの返事や終了コードだけで成功と決めず、仕事がどう進み、環境に何が残ったかを確かめる。

五つの言葉を、まず区別する

言葉平たく言うとLife Managerの例
log起きたことの時刻付き記録。記事のquality gateがFAILした。
trace / span一回の仕事と、その中の各処理の道筋。research → draft → reader gate → publish check。
observability出ている情報から、既知・未知の問題を調べられる力。どのjobが何のreleaseで止まり、次に何を確認するか。
traceability仕事と実行・結果・根拠を結び付け、後からたどれること。task → occurrence → run → receipt → money record。
eval実際の結果を、事前に決めた成功条件で採点すること。記事が公開され、公式入金と費用を確認できたか。

OpenTelemetryはobservabilityの共通標準です。logsは時点ごとの記録、metricsは集計値、tracesは親子関係のある処理経路です。traceは観測方法の一つで、traceabilityは仕事の証拠一式をつなげる性質です。OpenTelemetry observability primer

health checkは「今、決めた条件を満たすか」を確認します。evalは「依頼した仕事が成功したか」を判定します。workerが起動していることと、顧客の仕事が終わったことは別です。

Life ManagerのCLIは、評価を始める入口になる

最新mainには、owner・run・occurrence・release SHA・phase/status・failure layer・error class・次のaction・provider receipt ID・official readback referenceなどを持つstructured runtime eventがあります。schemaで値を検証し、secretらしい値を拒否またはredactして、private JSONLへ追記します。

./bin/lm-loop status --explainとhealth --jsonは、status rowsから読み取り専用のhealth projectionを返します。doctorはregistry、ロード済みlabel、entrypointを確認します。health observerはsnapshotのhistory、状態変化時のalert、recovery intentを保存します。

だからCLIは役立ちます。「どのownerのどのrunを見るか」を決め、既存eventへ進む入口になります。ただし、health表示もrecovery intentも、そのまま仕事の成功ではありません。Life ManagerのREADMEは、registryへの登録、health、外部effectの成功を分け、business successはofficial provider receiptで確かめると説明しています。

source確認：今回調べたruntime/evalの範囲では、OpenTelemetry SDKとtrace_id/span_idによるspan計装は見当たりませんでした。独自のruntime eventとhealth observerはあります。まず既存eventをevalへつなぎ、追加のtrace backendが必要かを見ます。

完了・公開・入金は、別々のoutcome

Writerがreader gateに通ったことは記事品質のoutcome。公開URLが確認できたことはpublisherのoutcome。顧客の購入・settlementが確認できたことは金銭のoutcomeです。利益を言うには、手数料・返金・AI/API費用のcoverageも必要です。費用が欠けたらnetはunknownにします。

既存LM-EABは、現在、合成fixtureで会計・自律性のcontractを検査するoffline evaluatorです。guideは、それが実agentを実行したり収益を生んだりする試験ではないと説明しています。

形式を示す架空例：
task_case_id        → Writerの評価問題
business_occurrence → この記事を作る業務のまとまり
run_id              → 一回の実行試行
release_sha         → 動いたsourceの版
trace               → research → draft → gates
outcome             → gate結果・公開状態・official receipt
money outcome       → 入金・返金・fee・費用・coverage
evaluation record   → grader版・結果・理由・根拠参照

識別子は説明用の例で、Life Managerの新schemaではありません。

traceabilityを上げる方法は、全文をログへ複製することではありません。安定したID、版、stage、判定、evidence referenceをつなぎ、記事本文や顧客情報は所有元のprivate storeに置きます。

良いevalは、実際の失敗から作る

  1. 成果を一文で決める。「AIが良い記事を書く」では曖昧。「この記事を読む人が、何を判断できるか」と書く。
  2. 自然な失敗のtraceを読む。research、draft、fact check、公開、receipt照合のどこで失敗したか分類する。
  3. 初期状態と制約を固定する。入力、利用可能tool、予算、期間、終了条件を明記する。
  4. 正解例を用意する。taskを正しく解いたものがgraderに合格するかを確かめる。
  5. 対照例も入れる。安全に止まるだけでなく、正しく仕事を進める例も試す。
  6. 確認できるものはコードで採点する。hash、必須項目、公開状態、receipt、費用coverageなど。
  7. 解釈が必要ならrubricを使う。LLM judgeを人の判断例と比べ、失敗理由を読み較正する。
  8. 同じ条件でbaselineとcandidateを比べる。dataset・grader・release版、trial数、費用を記録する。

Anthropicのガイドは、実際の失敗から20〜50件ほどで始める考え方、reference solutionでgraderを点検すること、traceを読み採点ミスを探すことを紹介しています。数は絶対条件ではなく、初期signalを得る目安です。Anthropic: Demystifying evals for AI agents

自己修復と自己改善は、同じ評価に別の質問をする

自己修復自己改善
質問失敗後、仕事を安全に正しい状態へ戻せたか。動いている仕事から、baselineより良い成果を出せたか。
採点例回復後の完了、再発、重複、復旧時間、人の介入。reader value、settled net、cost、latency、人の介入。
誤判定processが再起動しただけで修復成功とする。quality gateが上がっただけで売上改善と言う。

GEPAのprompt optimizerやOpenEvolveの候補探索は、traceや評価feedbackから改善案を作れます。ただしcandidateがgraderや安全境界を書き換えられないようにします。回数上限で失敗したら止めて原因を記録し、外部effectがunknownなら公式readbackまで再送しません。

記事2 · Life Managerのpilot

Writerの一記事から、品質evalと実収益readbackをつなぐ

Writer全体の作り直しではなく、既存gateのある公開前の一記事で、self-healingと比較評価を試す。

Writerは、記事editorial/reader/identity/safety gate、失敗後のreroute、失敗が続けばblockする上限、公開後のmoney ledgerを既に持っています。このため最初のpilot候補にできます。ただし測定を一度に全部広げません。

最初のcase：読者の疑問、参照資料、禁止claim、draft hash、grader版を固定し、公開前記事を評価します。実際に落ちたgateとその理由をtraceへ結び、同じcaseでreroute後を評価します。safety failureは公開へ流さず、上限に達したらblockします。

自己改善：baselineのoutline/promptと、一要素だけ変えたcandidateを同じcaseで比較します。editorial/readerの採点、事実の根拠、利用費、時間、reroute回数を別々に残します。LLM judgeは人の判断例と較正します。

実収益：公開URL、顧客購入、settlement、refund、fee、AI/API費用を同じarticle IDと期間で公式記録に結びます。品質gateのPASSから売上を推定しません。receiptや実費coverageが欠けたら、netはunknownです。

pilotのdone：失敗traceから原因を見つけ、同じcaseで一回のbounded recoveryまたはcandidate比較を再現できる。publicationと金銭outcomeは、公式receiptが得られた場合にのみ別途記録する。合成caseならsyntheticと明記する。

Writerが「18業務で最も簡単」と証明済みではありません。選ぶ理由は、既存quality gateと金銭readback経路が同じ業務にあること、公開前部分を安全に繰り返し評価できることです。Connectorのような業務完了の簡単さより、収益目標に近い開始点です。
